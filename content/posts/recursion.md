第一次写递归时，最容易产生的疑问是：函数一直调用自己，为什么不会永远转下去？

答案不在“浏览器会帮你停”，也不在“调用栈有上限”。真正让递归成立的是两件事：

1. 有一个**终止条件**；
2. 每一次递归调用，问题都严格地变小。

这两件事合起来，保证递归不会无限进行。

## 从阶乘开始

阶乘的定义几乎是照着递归写的：

```js
function factorial(n) {
  if (n === 0) return 1;
  return n * factorial(n - 1);
}
```

$n=0$ 是终止条件。对 $n>0$，问题从 $n$ 变成 $n-1$，规模严格下降。

所以调用链一定会在有限步后到达 $0$：

$$
n \to n-1 \to n-2 \to \cdots \to 0.
$$

如果少了终止条件，函数就会一直调用下去；如果每次调用没有让问题变小，递归同样不会结束。

## 递归和归纳是同一件事

数学归纳法说：

- 验证最小情形；
- 假设 $n$ 成立，证明 $n+1$ 也成立。

递归写的是同一件事，只是方向反过来：

- 最小情形直接返回；
- 较大问题归约到较小问题。

所以递归函数的正确性，通常也用归纳法证明。终止条件对应归纳起点，递归步骤对应归纳假设。

> 递归不是“自己调用自己”的技巧，而是一种把无限多的情况压缩成有限条规则的构造。

## 调用栈里发生了什么

递归函数并不是同时做很多事。每次调用都会在调用栈上留下一帧，保存当前的参数和返回地址。

以 `factorial(3)` 为例：

```text
factorial(3)
  factorial(2)
    factorial(1)
      factorial(0)  -> 1
    <- 1 * 1 = 1
  <- 2 * 1 = 2
<- 3 * 2 = 6
```

先一路向下，直到碰到终止条件；再一路向上，把结果乘回去。

如果递归太深，调用栈会耗尽，这就是栈溢出。但栈溢出不是递归“不收敛”的证明，它只说明这个实现消耗了太多栈空间。

## 一个不那么明显的例子

二分查找也可以写成递归：

```js
function binarySearch(arr, target, lo = 0, hi = arr.length - 1) {
  if (lo > hi) return -1;

  const mid = Math.floor((lo + hi) / 2);
  if (arr[mid] === target) return mid;

  return arr[mid] < target
    ? binarySearch(arr, target, mid + 1, hi)
    : binarySearch(arr, target, lo, mid - 1);
}
```

这里的“严格变小”不是 $n$ 减一，而是搜索区间每次至少缩短一半。

递归能否终止，不取决于参数是否总在减小，而取决于是否存在一个**良基的度量**：每次调用都让这个度量向最小值靠近，并且不可能无限下降。

在阶乘里，度量是 $n$；在二分查找里，度量是区间长度。

## 并不是所有递归都值得写

递归很适合描述分治、树、图、回溯和数学归纳结构。

但对于简单的线性循环，递归可能只是把 `for` 换了一种写法，还额外消耗了栈。比如计算斐波那契数列时，直接照抄定义会重复计算大量子问题：

$$
F(n)=F(n-1)+F(n-2).
$$

这不是递归本身的问题，而是没有复用子问题的结果。加一个记忆化数组，或者改成自底向上的循环，复杂度就会从指数级降下来。

> 递归负责表达结构；动态规划负责避免重复。两者不是对立的。

## 最后

递归之所以能停下来，是因为我们在写它的时候，悄悄证明了一个终止性命题：

> 每一次调用，问题都在某个良基度量上严格变小。

终止条件只是这个证明的起点。真正让递归可靠的，是那个不断下降的度量，以及我们对它的归纳。

写递归时，先问自己：**什么在变小？** 这个问题比“终止条件写了吗”更接近本质。
